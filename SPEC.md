# Cache Memory Simulator: Specification

## What this project does
A trace-driven, cycle-accurate simulator of a cache hierarchy for a single in-order processor. We feed it memory access traces, and it reports hit/miss behavior, total cycles and average memory access time (AMAT).

## Out of scope
Multicore/coherence, out-of-order execution, virtual memory and TLBs, DRAM internals, prefetching.

## Trace format
One access per line: <type> <hex address> 0 = data read, 1 = data write, 2 = instruction fetch 32-bit byte addresses.

## Hierarchy
- Split L1 (instruction cache + data cache)
- Unified L2
- Main memory
- Default: L1 = 32 KB, 4-way, 64 B blocks. L2 = 256 KB, 8-way, 64 B blocks
- Every parameter is configurable

## Mapping techniques
Direct-mapped, N-way set-associative, fully associative.

## Replacement policies
LRU, FIFO, Random (fixed seed so runs are repeatable).

## Write policies
- Write-back + write-allocate
- Write-through + no-write-allocate

## Timing model (cycles)
- L1 hit: 1
- L2 hit after an L1 miss: +10
- Main memory access after an L2 miss: +100
- Writing back a dirty block costs the access time of the next level
- Accesses are handled one at a time (blocking), no overlap
- Write-through sends one 4-byte word to the next level (traces carry no size)
- A dirty L1 block written back into L2 is a full-block overwrite, so an L2 miss on it does not fetch from memory
- L2 block size must be at least as large as the L1 block size

## Metrics
- Hits, misses, miss rate for every cache
- Total cycles and AMAT
- Writebacks and memory traffic
- Miss types (3C model): compulsory, capacity, conflict

## Experiment settings
Default hierarchy unless stated. "L1" means L1I and L1D set to the same size.
1. Size: L1 1-64 KB on random, vecadd, matmul ijk, matmul blocked
2. Associativity: 1, 2, 4, 8, fully associative on vecadd (32K), strided (32K), matmul ijk (8K); miss rate split into compulsory/capacity/conflict
3. Block size: 16-256 B on random, vecadd (32K), matmul blocked (4K). Memory latency grows with block size: 60 cycles + 5 cycles per 8 bytes (100 at 64 B)
4. Replacement: LRU, FIFO, Random (seed 0) on vecadd (2-way, 32K) and the three matmul orders (4-way, 4K)
5. Write policy: L1D+L2 as WB+WB, WT+WB, WT+WT on vecadd (32K) and matmul (4K). There is no write buffer, so every write-through write stalls the processor
6. L2: none, 64, 128, 256, 512 KB on sequential, random, vecadd (32K L1D) and matmul ikj (4K L1D)
7. Matmul: ijk, ikj, blocked (8x8 tiles) with L1 2-32 KB

## Validation
Small traces worked out by hand, with unit tests checking the simulator gives the same answers.

## Workloads (generated by cachesim/tracegen.py, fixed seeds)
- sequential: 256 KB array read front to back, 2 passes
- strided: one word every 256 B over a 128 KB array, 50 passes
- random: 200,000 random word reads in a 512 KB working set
- vecadd: c[i] = a[i] + b[i], 16384 elements, 2 passes, 6-instruction loop body
- matmul: 64 x 64 matrices, C[i][j] += A[i][k] * B[k][j], loop orders ijk,
  ikj and blocked (8 x 8 tiles). Every order does the same 4 accesses per step.
Matrix multiply experiments use a 4 KB L1D: with 32 KB the whole of B fits
and every loop order looks the same.
